No Repository: (It is what we have in the very beginning)
Controller, EF or Dapper or ADO, Database, they are tightly coupled with each other.
1. Hard to mock EF or Dapper method so that cannot do unit testing. In this case only integration testing works. It is ok when the app is small. What if it is as big as send voucher in TX2. That will be super hard to troubleshooting.
2. What if one day we want to change EF to be Dapper? It will cause many bugs.

Repository: (It is what we have right now)
Group all of the related operations together in a clsss. For example, group all of product related operations together in ProductRepository. 
Group all of client related operations together in ClientRepository.
1. Easy to mock EF or Dapper or ADO operations so that we can write unit test.
2. It is easy to change technology. like changing from ADO to Dapper.


Repository + UnitOfWork
1. Unit of work is like a facard pattern. 
With out unit of work, you need to inject many repositories into controller.
With unit of work, you just need to inject an unit of work object so that you can access all of the repositories throught the single unit of work object.
2. Unit of work also group operations together in one transaction which shall either success all together or fail together.
For example there is an operation called create clients. In order to create a client, need to have three operations.
1. In ClientRepository, generate a client code. 2. In AddressRepository, generate an address and get addressId. 3. In ClientRepository, generate a client with the new generated client code and address id.
If any of these three opreations failed, everything shall be rolled back.
We must make sure that all of these three operation are successfully completed, then a client shall be created in the database.
